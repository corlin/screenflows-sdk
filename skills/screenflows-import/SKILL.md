# 准备离线导入数据

依赖 `screenflows` MCP 服务（只读）。本 Skill 在用户自己的数据或代码仓库里工作：写导出 / 转换脚本、生成文件、做本地检查。上传由用户在 ScreenFlows 网页右上角「导入数据」中完成（MCP 不上传文件）。

## 步骤

1. **读规范**：调用 `get_import_spec`，以它返回的字段、时间格式、隐私规则为准（下文是摘要）。
   - 必填：`user_id`（同一个人保持一致的匿名 id 也可以）、`event`（页面路径 / 完整地址 / 事件名）、`timestamp`
   - 可选：`session_id`（没有就按 30 分钟无操作自动切分）、`url`、`referrer`，其余列作为属性（最多 20 个，如 `device`、`channel`、`city`）
   - 每行一个事件；格式 CSV（UTF-8）、TSV、JSONL、Parquet；1GB 以内，首批建议 100 万行以内

2. **摸清数据源**：找到事件表 / 日志 / 导出文件，确认：
   - 哪一列能稳定标识一个人（登录用户 id 优先，其次匿名 id / 设备 id；不要用会话 id 代替用户 id）
   - 页面用什么表示：路径、完整地址，还是事件名（`page_view` 这类通用事件名要换成具体页面路径，否则整个网站只有一个"页面"）
   - 时间列的格式与时区（服务器 UTC 还是本地时间；导入时要选对时区）
   - 是否混有机器人 / 监控探测 / 内部测试账号，能过滤就先过滤

3. **转换**：写一个可重复执行的脚本（Python pandas 或 SQL 导出），输出规范列名。要点：
   - 页面事件和关键交互事件（加购、提交、支付成功等）都保留；高频噪声事件（滚动、心跳、曝光）去掉
   - 转化目标事件一定要包含（如 `/pay/success`、`order_paid`），否则无法计算转化
   - 地址里的商品 id、订单号会被自动归并为 `:id`，不用手动处理；查询参数会被去掉
   - 时间统一成 ISO 8601（最好带时区，如 `2026-10-01T09:00:00+08:00`）或 13 位毫秒时间戳
   - **个人信息**：手机号、邮箱、身份证、姓名、地址、IP 不要导出；用户 id 如果本身是手机号 / 邮箱，先做不可逆哈希（如 SHA-256 加盐）
   - 数据超过 100 万行时，按时间截取最近一段，或分多个文件后用"追加"导入

4. **本地检查**（导入前跑一遍，把结果告诉用户）：
   - 行数、用户数、时间范围；三个必填列的空值比例（超过 5% 要查原因）
   - 不同页面 / 事件的数量（只有个位数说明 event 列取错了；上万个通常是没归并的原始地址或带了参数）
   - 每个用户的平均事件数（接近 1 说明 user_id 每次都变，路径无法串起来）
   - 访问量最高的 20 个页面 / 事件，以及候选转化目标出现的次数
   - 再确认一次没有个人信息列

5. **上传与确认**：告诉用户在 ScreenFlows 网页点「导入数据」→ 选组织与项目（新建，或已有项目选"追加 / 替换"）→ 选时区 → 上传文件 → 核对校验报告与字段对应 → 确认导入 → 确认转化目标与漏斗。只有分析师及以上角色能导入。

6. **跟进**：用 `list_imports` 查看状态（`analyzed` 表示等用户确认，`ready` 为完成，`failed` 看 `error`）。完成后可以接着用 `screenflows-review` 等 Skill 分析新项目；页面名称（中文名、所属阶段）可以按 `screenflows-data-health` 的方式整理好，让用户在「业务语义配置」中上传。

## 输出

- 转换脚本（放在用户仓库里，附运行方法）与生成的文件路径
- 本地检查结果表
- 需要用户在导入时选择的设置：时区、导入方式、建议的转化目标与漏斗步骤

## 原则

- 不确定的列含义先问用户，不要猜测哪一列是用户 id 或转化事件。
- 不把原始数据内容（尤其是用户 id 与地址）大段贴进对话；检查结果只给统计值和少量脱敏样例。
