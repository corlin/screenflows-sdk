# ScreenFlows 周期复盘

依赖 `screenflows` MCP 服务（工具名形如 `mcp__screenflows__get_overview`）。如果工具不可用，提示用户在 ScreenFlows 网页右上角「MCP 令牌」生成令牌并按说明接入，不要编造数据。

## 步骤

1. **确定项目和时间窗口**
   - 调用 `list_projects`，确认项目 id、转化目标和数据日期范围 `dataRange`。
   - "上周 / 近 7 天 / 上个月"一律以 `dataRange.to`（数据最后一天）为结束日推算，不要用今天的日期；向用户说明实际使用的起止日期。
   - 数据跨度不足两个窗口时，改为只看本期并说明原因。

2. **总览与对比**：`get_overview`（`compare_previous: true`，带 `from` / `to`）。记录：
   - 会话数及变化、到达目标的比例变化（百分点）、平均到达步数变化、主要入口是否变化。
   - `dataQuality.level` 为样本有限或不足时，在报告开头写明，后续结论都标注"仅供参考"。

3. **定位变化来源**（按需，别全部调用）
   - 转化率变化明显 → `get_funnel`（本期）：找流失最大的一步和流失去向；必要时对上期窗口再调一次比较同一步。
   - 想知道路径怎么变 → `get_flow`（`compare: "previous_period"`, `max_edges: 20`）：看 `diff` 绝对值最大的连线、`bounceRateA` / `bounceRateB` 差异大的页面。
   - 分群差异 → 先 `list_segments`，再对关键分群调用 `get_overview`。

4. **给出建议**：对 1～2 个最关键的页面调用 `diagnose_page`，必要时 `simulate_intervention`（默认 15%）估算影响。

## 输出格式

```
## <项目> 复盘：<本期起止> vs <上期起止>
**一句话结论**：……
### 关键指标
| 指标 | 本期 | 上期 | 变化 |
### 发生了什么（每条附数据证据，如「购物车→购买成功 流失 68%（上期 75%），92 位进入上一步」）
### 建议（按优先级，每条注明依据与预期影响；推演结果写明「模型估算，需 A/B 验证」）
### 数据说明（窗口、样本量、注意事项）
```

## 原则

- 只报告工具返回的数字，不推测没有数据支撑的原因；相关不等于因果。
- 差异小于 1 个百分点或样本不足 30 个会话的页面，不下结论。
- 推演是马尔可夫路径模型估算，不是承诺效果。
