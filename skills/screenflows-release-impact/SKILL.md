# 发布影响评估

依赖 `screenflows` MCP 服务。

## 步骤

1. **确定窗口**
   - 向用户确认上线日期 D 和关心的功能 / 页面（可从 git 提交记录或发布说明中获取）。
   - `list_projects` 查看数据范围。上线后窗口 = D 至 `min(D + N - 1, dataRange.to)`；上线前窗口 = 与之等长、紧挨 D 之前。N 默认 7 天；上线后数据不足 3 天时，提示用户稍后再评估。
   - 窗口内若有大促、节假日等干扰，提醒用户。

2. **整体变化**：`get_overview`，`from` / `to` 设为上线后窗口，`compare_previous: true`（工具自动取等长的上线前窗口）。

3. **聚焦受影响的部分**
   - 改动涉及的页面：`get_flow`（`compare: "previous_period"`），看该页面的离开率（`bounceRateA` vs `bounceRateB`）和进出连线概率的 `diff`。
   - 涉及转化步骤：`get_funnel` 分别对两个窗口调用，比较同一步的转化率和流失去向。
   - 只影响部分用户（如移动端）：带上 `segment` 重复以上步骤。

4. **判断可信度**
   - 每个窗口的 `dataQuality.sessions`；页面级比较要求两期都至少 30 个会话。
   - 差异很小（< 1 个百分点）或样本不足时，结论写"暂无法判断"。
   - 前后对比会受季节、流量来源变化影响，不等同于 A/B 实验；需要严格结论时建议做 A/B。

## 输出格式

```
## <功能> 上线影响（上线 <D>；对比 <上线后起止> vs <上线前起止>）
**结论**：正面 / 负面 / 暂无法判断 —— 一句话理由
| 指标 | 上线后 | 上线前 | 变化 |
### 受影响页面与路径（附数据）
### 风险与干扰因素
### 下一步（继续观察多久 / 是否需要 A/B / 需要补的埋点）
```
