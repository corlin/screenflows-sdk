# 用数据驱动的页面优化

依赖 `screenflows` MCP 服务。在产品代码仓库里使用（例如项目对应的前端仓库），这样才能定位并修改页面代码。

## 步骤

1. **找准页面**
   - `list_projects` 确认项目；`get_flow`（`max_edges: 15`）或 `get_journey` 找到目标页面的 `page` id 与名称。
   - 用户没指定页面时，从 `get_overview` 的漏斗断点和 `get_flow` 中离开率高、访问量大的页面里挑 1～2 个，并说明理由。

2. **诊断**：`diagnose_page`（可带用户关心的 `from` / `to` 或 `segment`），读：
   - 访问会话数、离开率与全站平均、占全站离开的比重；
   - 与哪个页面来回往返（说明信息不足、需要来回比对）；
   - 推荐的干预方案（触发时机、呈现形式、目标动线）及其评级。

3. **评估影响**：`simulate_intervention`，按 10% / 20% 两档估算目标转化的变化，作为优先级依据（写明是模型估算）。

4. **定位代码**
   - 根据页面路由或名称在仓库中搜索对应的路由配置与页面组件（如 `routes`、`pages/`、`app/` 目录，或页面标题文案）。
   - 阅读组件后，把干预方案翻译成具体改动：放在哪里、展示什么、点击去哪里、埋点事件名。

5. **提出方案并等待确认**：列出改动点、影响范围、需要的数据或接口。**得到用户确认后再改代码。**
   - 改动用功能开关或实验分组包住，方便 A/B 和回滚；新增的点击 / 曝光要有埋点，事件名与现有页面路由体系一致，否则 ScreenFlows 无法识别。
   - 新页面或新路由需要同步到 ScreenFlows 的页面字典（提醒管理员在「业务语义配置」中补充）。

6. **验证方案**：说明上线后如何验证，例如上线日为 D，用 `get_overview` 对 D 之后与之前等长窗口 `compare_previous`，并观察该页面在 `get_flow` 中的离开率与目标方向连线概率；同时关注 `dataQuality` 样本量是否足够。

## 原则

- 不要在没有用户确认的情况下修改代码或发布。
- 只引用工具返回的数据；推演结果不是效果承诺。
- 改动保持最小、可回滚，遵循仓库现有的代码风格与组件。
